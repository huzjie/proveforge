# 可验证推理（Provable Inference）原理

## 要解决的问题

调用大模型时，存在一个结构性信任缺口：

- 你无法确认返回的 token 是**你付费的那个模型**算出来的；
- 路由服务可能悄悄换成一个更便宜的模型；
- 攻击者可能在传输中篡改 token 流。

内容真假是另一回事（内容溯源 ≠ 内容真实），可验证推理只回答一件事：**这个输出是不是「那个模型」算出来的。**

## 三步协议

### 1. Commit —— 先承诺，后服务

提供方对权重做 Merkle 承诺，发布一个根哈希。承诺的性质：

- **隐藏性**：根是单向哈希，反推不出权重；
- **绑定性**：任何权重变化都会改变根。

### 2. Prove —— 每次回复附一张收据

对每个 prompt，提供方记录完整执行轨迹，并用 Fiat-Shamir 挑战决定揭示哪些权重行。证明携带：输出 token、被打开的行 + Merkle 兄弟路径、执行轨迹。

### 3. Verify —— 任何人廉价校验

验证器重导出挑战，检查两类关系：绑定（打开的行能否导出承诺根）与完整（轨迹自洽、argmax 与输出一致）。

## 本参考实现的取舍

| FlashProve | 本仓库 |
|---|---|
| 真 zkSNARK，隐藏权重 + 激活 + 路由 | 透明证明 + 选择性揭示，隐藏权重、不隐藏激活 |
| 400B MoE，4-bit，H100 ~110 tok/s | 整数小模型，CPU 毫秒级 |
| 证明 ~19 MB / 1024 token | 证明 ~1 MB |
| 形式化验证（Lean） | 「测试过、未验证」，口径一致 |

关键保留的**可复用骨架**：Merkle 承诺 + Fiat-Shamir 挑战 + 选择性揭示 + 非对称成本（证明贵、校验便宜）。

## 为什么「选择性揭示」就能抓造假

偷换模型的证明者只能揭示「假模型」的权重，而这些权重哈希不到「真模型」的承诺根。因为挑战是证明者无法预知的（由承诺+输出+轨迹哈希决定），他无法只伪造「不会被抽查的部分」——打开的行越多，漏网概率越低。这就是声音性（soundness）随打开比例上升的由来，也是 zkSNARK 中「IOP + 多项式承诺」思路的朴素原型。
